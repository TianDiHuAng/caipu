## 一、项目概述

### 1.1 项目是什么

caipu 是一个**中外菜谱网站 monorepo**：以中文为主、兼顾英文的多语言菜谱内容平台，同时提供网站前端与后端 API。核心定位是构建一个可检索、可筛选、支持份量换算的菜谱数据库，并对外提供 RESTful API。

### 1.2 技术栈

| 层级 | 技术 | 说明 |
| --- | --- | --- |
| 前端 | Next.js + TypeScript + Tailwind CSS | apps/web，含首页、分类树、菜系列表、菜谱详情、搜索页、食材反查、打印视图等页面 |
| 后端 | Fastify | apps/api，提供 `/api/v1/meta`、`/recipes`、`/search`、`/filters`、`/ingredients`、随机推荐等接口 |
| 数据库 | SQLite（better-sqlite3） | data/db/caipu.sqlite，Drizzle ORM schema（SQLite→PostgreSQL 可迁移） |
| ORM | Prisma / Drizzle | packages/db |
| 测试 | node:test | tests 覆盖导入脚本自动化、API 冒烟、schema 校验等 |
| 部署 | Docker Compose | Dockerfile 多阶段构建 + tini + healthcheck，容器入口 `scripts/docker-entrypoint.sh`（建库→导入→起 API→等就绪→起站点） |

### 1.3 菜谱规模目标

- **总目标：3274 道菜谱**
- 分类体系：**59 个菜系 × 26 个品类**，共 **639 个格子**（progress.json totals.cells）
- 格子目标由 tier 推导：A 级核心品类 15 道/格、扩展品类 8 道/格（4 个）；B 级 6/4；C 级 5 道/格（仅核心品类）
- 数据源：data/taxonomy.json（菜系表）、data/ingredients.json（食材词典，约 430 项）、scripts/lib/rules.mjs（校验规则）

## 三、生产流程与批次体系

### 3.1 固定生产套路（不可改动）

```
1. 生成草稿   temp/drafts/batch-NN.json    （用短键省 token）
2. author.mjs 展开正式字段 + 查食材词典 → data/recipes/{region}/{cuisine}/{id}.json
3. validate.mjs 校验修到 0 错误
4. import.ts 导入数据库（宿主 Node 是 22，须先 set PATH=D:\Node;%PATH%）
5. npm run progress 更新 progress.json 与 TASKS.md 勾选
6. git add -A && git commit（写明本批菜系与菜名）
```

### 3.2 草稿结构约定

草稿使用短键以节省 token，author.mjs 自动映射为正式字段：

- 配料键：`{n, a, u, note}`（名称、数量、单位、备注）
- 步骤键：`{t, time, heat, tip, cue}`（文本、时长、火候、提示、感官线索）
- 菜谱级键：id / zh / en / original / cuisine / category / difficulty / prep / cook / servings / flavor / ingredients / equipment / steps / tips / mistakes / subs / variations / serving / storage / nutrition / safety / origin / tags / related
- 时间合计：time.total_min = prep_min + cook_min
- overwrite:true 才覆盖已有文件（默认跳过）

### 3.3 批次编号规则

- 批次号连续递增：batch-01.json → batch-02.json ……
- 已提交的批次文件仍保留在 `temp/drafts/` 中（历史存档用途）
- 分批失败或拆分时追加 `-p1` `-p2` 后缀（如 batch-137-p1.json）
- 废弃修复稿以 `_fix` 前缀命名（如 `_fix1.json`）
- 新批次号接续 temp/drafts/ 中最大编号继续

### 3.4 校验与审计机制

- **validate.mjs**：runRecipeRules（R1-R9 规则）+ runGlobalRules（id 唯一、related_ids 有效、路径一致）+ runDuplicateCheck（20 字滑窗雷同检测，阈值 5）
- **audit.mjs**：每约 10 批执行一次 5% 随机抽检，评分写入 tasks/AUDIT_REPORT.md
  - 评分维度：准确性(25)、完整性(25)、可操作性(30)、安全性(20)，等级分 A/B/C/D
  - C/D 级按报告明细重写
- **import.ts**：JSON 源数据幂等导入数据库（recipes 表 id 一一对应）
- **progress.json**：totals.target/target 由 tier 推导，actual 为「菜谱×品类」格子累加值（一道菜多品类会重复计，属正常口径差异）

## 四、核心约束红线

### 4.1 枚举值限制（严禁越界）

| 字段 | 限制 | 示例禁区 |
| --- | --- | --- |
| category | taxonomy.categories 合法 slug | 不得自造品类名 |
| group | 仅限 main / seasoning / garnish 等分组 | 不得使用其他分组名 |
| unit | 仅限 g/ml/piece/clove/slice/stalk/pinch/to-taste 等 | **禁「个」**，改用 piece |
| flavor | 风味枚举值 | **无 creamy/crispy/fresh** |
| heat | 火候枚举值 | **无中高火/高温** |
| cuisine.style | taxonomy.cuisines.slug | 不在表中即报错 |

### 4.2 食材词典泛称禁止

- 配料表里的食材必须在 steps/tips 中出现，反之亦然（R4 互相引用检查）
- **禁用泛称词条**：瘦肉、鸡、辣椒、蒜 等一旦进词典，会让既有菜谱写「瘦肉」的步骤突然报错
- 统一写法：猪里脊、鸡腿肉、大蒜、小米辣
- 单字食材名（如「虾」）无法被 coveredByDeclared 豁免，含虾菜品慎用「虾仁」写法，或改用干贝、干鱿鱼丝等词条
- author.mjs 会规范化菜名（牛腱肉→牛腱、河虾仁→虾仁），步骤文本须按落库名书写
- 步骤里的比喻别用食材名（如「黄豆粒大小」判为未登记黄豆），改用「小指盖大小」

### 4.3 文本长度下限

| 字段 | 下限 | 备注 |
| --- | --- | --- |
| 步骤文本 s.text | ≥ 20 字 | 需含动作+火候+时间+感官线索 |
| visual_cue | ≥ 8 字 | 外观/气味/口感判断依据 |
| tip | ≥ 6 字 | 步骤内提示 |
| tips[i] | ≥ 8 字 | 独立贴士条目 |
| food_safety_notes[i] | ≥ 15 字 | 安全提示条目 |
| common_mistakes | ≥ 15 字 | 常见错误每条 |
| origin_note | ≥ 40 字 | 来源说明 |
| substitutions/variations | ≥ 15 字 | 替代/变体每条 |

### 4.4 高风险食材安全提示强制

含鸡蛋/豆角/四季豆/木薯/河豚/菌菇/木耳/银耳/生蚝/牡蛎/蛤蜊/生食类/鸡肝/猪肝/鸡蛋/蛋黄/鸭蛋时，`food_safety_notes` 必须出现「安全/彻底加热/中心温度/熟透/不要生食/冷藏」之一，否则 R9 报错。

### 4.5 图片占位原则

- 图片资源统一走占位策略（ISR/SSG 静态化），不依赖外部图片服务
- 打印视图 /recipes/[id]/print 独立渲染，确保离线可用
- 具体实现细节见 apps/web 相关组件与 DEPLOY.md

### 4.6 多语言字段支持

- 数据层 name{zh,en} 双语言存储
- 前端 zh/en 字典 + locale 路由切换（?lang= 参数与 cookie）
- 搜索层同义词表 + pinyin-pro 全拼/首字母扩展 + 权重排序
- 多语言验收已在 STAGE_REPORT 阶段 5 记录通过

### 5.3 步骤文本被词典别名误报规避

rules.mjs 的 matchIngredients 采用最长匹配优先且消耗型匹配（consumed 数组防重叠）。写作时需避免在步骤中使用可能命中别名的词组，否则会被误判为「提到某食材但配料表没有」。例如「淀粉」「奶油」「肉馅」「肉末」等常见表述若恰好是某个登记食材的别名，就会触发 R4 报错。对策：步骤文本尽量用落库规范名书写，比喻不用食材名。

### 5.4 related_ids 必须引用真实 id

runGlobalRules 强制检查 related_ids 中的 id 必须存在于 byId map 且不能包含自身。跨菜系引用前先确认 id 存在，否则直接报错。

### 5.5 unit 禁止「个」，改用 piece

unit 枚举不含中文量词。「个」会被判定为非标准单位而报错，统一改为 piece（配合 PROTEIN_PER_PIECE 换算克重）。

### 5.6 flavor 无 creamy/crispy/fresh

flavor 枚举不包含这些描述性词汇，写错即触发分类一致性检查报错。应选用 taxonomy 定义的风味标签。

### 5.7 heat 无中高火/高温

heat 枚举仅包含标准火候档位，「中高火」「高温」等非标准表述会报错。

### 5.8 时间合计必须对齐

time.total_min 必须等于 prep_min + cook_min（允许 ±5 分钟误差），否则 R3 用量合理性检查报错。若含并行工序，需下调单步时长并在 tip 里注明「可提前熬制」。

### 5.9 配料未被使用须加表述

ingredients 中声明的食材必须在烹饪步骤本体（steps text/visual_cue/tip）中被提及或使用，否则 R4 报错。如果确实不需要出现在步骤里，需在旁述字段（tips/substitutions/variations）中补充合理表述，否则仍可能被判定违规。

### 5.10 其他高频坑点

- 「适量」字样禁止出现在任何步骤文本中，须给具体用量
- 每份盐 ≤ 6g（盐焗类铺锅粗盐写进 note，不要把总盐量堆到主料里）
- 每份主料总量 ≤ 700g（汤、高汤放 seasoning 分组，不要放 main）
- 油炸类总油量上限 270ml（非油炸 360ml）；「复炸」步骤必须写明植物油，否则判未使用
- 主料低于 60g/份 也会报错（份量或用量可能写错）
- 步骤序号 n 必须从 1 开始连续，否则报错
- 占位符 TODO/FIXME/TBD、省略表述「同上/同前/参照上文」、省略号均禁止

## 六、环境注意事项

- 宿主机默认 Node 版本为 **22**
- better-sqlite3 编译于 **Node 24**，两者 ABI 不兼容
- 凡涉及数据库的命令必须先设置 PATH：
  ```
  cmd /c "set PATH=D:\Node;%PATH% && npx tsx scripts/import.ts"
  ```
- npm test 也须在 Node 24 下运行（同样需要 PATH 设置）
- 历史修复记录：阶段 3 曾因 better-sqlite3 原生绑定缺失（ERR_DLOPEN_FAILED）而 npm rebuild better-sqlite3 重新编译恢复

### 6.2 git index.lock 守护进程重建问题

- `.git/index.lock` 可能被外部守护进程反复重建，导致 `git commit/push` 持续失败
- 绕过方式：将索引指向仓库外临时位置
  ```
  set GIT_INDEX_FILE=<仓库外临时路径>\index.lock
  ```
- 或者改用其他绕过方式（如先移除 lock 再操作，需谨慎确认无并发写入）
- 当前工作区仍存在 .git/index.lock 文件，属正常现象，不影响只读读取

### 6.3 GitHub 远端代理配置

- 远端仓库地址：https://github.com/TianDiHuAng/caipu.git
- 代理地址：http://127.0.0.1:10808
- 推送/拉取时需确保代理可用，否则 push 会失败
- 注意：git config 中未显式配置 http.proxy，代理通常由环境变量或外部工具链注入，提交前请确认网络环境

### 6.4 Docker 验证条件

- docker-compose 实跑验证依赖 Docker 守护进程
